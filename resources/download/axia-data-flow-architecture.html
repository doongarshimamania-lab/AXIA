1. Executive Summary

Axia is a payment protection platform for agencies and freelancers working on platforms like Upwork, Fiverr, and Toptal. The application is built on Vite + React 19 with a Convex backend, comprising 33 page components, approximately 48 query calls, and 68 mutation calls across the frontend. The Convex backend exports roughly 150+ query functions, 80+ mutation functions, and 1 action function across 60+ module files.

Key Finding

40-50% of backend queries are never called from any frontend page. The backend has been "forward-built" with extensive functionality (compliance alerts, protection plans, milestone tracking, evidence analytics, network connections) that has no corresponding UI. Conversely, a few pages (Projects, InvoiceBuilder, ProposalBuilder) render sparse or empty content when the backend is unavailable, lacking proper demo data fallbacks.

This document maps the complete data flow architecture: how users navigate the platform, which data flows between pages, which sub-components consume which queries, and where the critical gaps exist. The goal is to provide a clear roadmap for connecting the remaining dots so that every piece of backend functionality has a visible, usable frontend surface.

2. User Journey Map

2.1 Public Journey (Unauthenticated)

Unauthenticated visitors experience a streamlined funnel: they arrive on the Landing page, join the waitlist via the WaitlistForm, receive a referral code through the WaitlistSuccessModal, and can view their position on the WaitlistSuccess page. The only data interactions are waitlist mutations and referral stat queries. No dashboard or workspace data is accessible.

Landing page has zero data dependencies. WaitlistForm calls addToWaitlist mutation and getEntryByEmail query. SuccessModal calls getReferralStats query. The entire public journey is self-contained and works without authentication.

2.2 Authenticated User Journey

After authentication (via Google, GitHub, or email OTP on /auth), users enter the dashboard ecosystem. The ProtectedRoute component redirects unauthenticated users to /auth. The WorkspaceProvider wraps all routes, providing workspace context. The DashboardLayout provides a CollapsibleSidebar + main content area.

2.3 Client Portal Journey

Clients access the platform via a shared workspace token URL (/client-workspace?token=xxx). This route validates the token, then loads the client's projects, proposals, invoices, and team members. Clients can view proposals and invoices, mark them as viewed, and the system records their access. This is the only page that works with token-based authentication instead of user authentication.

Gap Identified

The client portal does NOT have pages for proposal signing or scope approval. The backend has proposals.crud.getProposalByToken and scope.crud.getScopeByApprovalToken queries, but no frontend routes exist for clients to view proposals or approve scopes via shared links.

3.2 Workspace-Centric Data Hierarchy

The workspace is the root container for nearly all business data. Each workspace has members, teams, channels, clients, and pipeline stages. Clients belong to a workspace and have projects, invoices, and deals. Projects have work sessions, evidence sessions, scope definitions, and protection scores. This hierarchy ensures data isolation between workspaces and provides the foundation for multi-tenant access control.

5. Cross-Page Data Dependencies

Several data entities are queried from multiple pages simultaneously. This creates shared dependencies where the same data must be consistent across views. The WorkspaceProvider acts as a shared context, but individual pages query the same data independently (Convex handles deduplication automatically).

Shared Data Pages That Query It Consistency Risk
clients (getClients / getClientsEnriched) Dashboard, Clients, PaymentPatterns, EvidenceExport Low - Convex real-time sync ensures consistency
invoices (getInvoices / getInvoiceStats) Dashboard, Invoices, PaymentPatterns, Subscription, InvoiceBuilder Low - same query function, Convex deduplicates
proposals (getProposals / getProposalStats) Dashboard, Proposals, ProposalBuilder Low - real-time subscription model
pipeline (getStages / getDeals / getPipelineStats) Dashboard, Pipeline Low - same workspace scope
scopeDefinitions Dashboard, Scope, EvidenceExport Low - read-only in Dashboard/EvidenceExport
workspaceId (from WorkspaceProvider) All workspace-scoped pages HIGH - If workspaceId is invalid/null, all workspace queries skip
Critical Dependency: workspaceId

The workspaceId from WorkspaceProvider is the linchpin of the entire data architecture. Nearly every page passes workspaceId to its queries. If the user has no workspace (e.g., first login before auto-seed completes), ALL workspace-scoped queries return undefined, and pages show empty/demo states. The WorkspaceProvider attempts to auto-seed a personal workspace, but if this mutation fails or is slow, pages render with no data.

6.3 Critical Missing Routes

These are entire pages that should exist but don't. They represent end-to-end gaps where the backend functionality exists but there's no way for users to access it:

CRITICAL GAP 1: Proposal Client View

Backend exists: proposals.crud.getProposalByToken returns a proposal by its public sharing token. proposals.crud.signProposal and proposals.crud.markProposalViewed handle client actions.
Frontend missing: No /proposal/view/[token] route exists. When a client receives a proposal link, they have no page to view or sign it. The entire proposal sharing workflow is broken at the receiving end.

CRITICAL GAP 2: Scope Client Approval

Backend exists: scope.crud.getScopeByApprovalToken and scope.crud.approveScopeByClient handle client-facing scope approval.
Frontend missing: No /scope/approve/[token] route. Clients cannot review or approve scope changes through the platform. This is a core value proposition feature that is entirely non-functional.

CRITICAL GAP 3: Project Detail Page

Backend exists: projectProtection.getProjectProtectionDetails, projectHealthDashboard, projectRiskTimeline, adaptiveEvidenceSystem, milestoneProtection - all return rich project data.
Frontend missing: The Projects page only shows a flat list. Clicking a project should navigate to a detail page showing health dashboard, risk timeline, milestone tracking, and protection score. None of this exists.

GAP 4: Invoice Client View

Backend exists: billing.crud.getByPublicToken returns an invoice by sharing token.
Frontend missing: No /invoice/view/[token] route for clients to view invoices externally. The ClientWorkspace page shows invoices, but direct link sharing doesn't work.

Summary

Axia has a robust backend with 150+ query functions and a well-structured workspace-centric data model. The frontend covers approximately 50-60% of this surface area with 33 pages, most of which are fully connected with demo data fallbacks. The three critical gaps are: (1) Proposal client view page, (2) Scope client approval page, and (3) Project detail page. Addressing these would close the most impactful end-to-end gaps. Beyond that, 11 backend feature areas have no frontend surface at all, representing significant untapped product potential.
